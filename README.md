# 工具调用：主动出击
传统对话系统中，知识召回通常通过召回排序流程实现，作为下游的回复生成部分要么是商家已经写好的答案，要么是基于召回知识进行简单优化模型；其有一个非常大的特点：回复生成的模型并不能直接干涉知识召回的流程。如果类比人工客服的工作流的话，就像是人工客服只能基于一套固定的知识回答用户的问题，而没有办法在他认为无法回答问题的时候，主动出击寻找他想要的知识。
﻿
然后大模型Agent来了。大模型强大的语义理解能力使得我们可以将大模型当作半个人工客服，赋予其主动寻找有效知识的能力，即工具调用的能力。基于这个思想，我们设计了第一版的售前Agent框架：

这里遵循了OpenAI的Tool-Use协议，希望用一个模型直接生成答案，发现知识不足时则调用工具寻找有效知识。为了业务效果，我们希望这版Agent可以遵守人工客服的售前流程SOP，因此我们对模型的Prompt使用了类似“状态机”的方法

## State Machine

在直接使用Function Call失败后，针对其“无法始终输出json”的问题，我们转而选择构建自己的协议，放弃function\_call模板。针对“无法follow人工SOP”的问题，考虑使用状态机的解法。其prompt例子如下：

```python

  ],
  "examples": [
    // list of short example scripts or utterances
  ],

    "arguments":[
        // parameter list
    ]
    "output":[
```

所谓状态机，就是通过人工定义SOP中各个节点的转移和吸收条件，并且要求LLM在输出中包含状态转移流程的方法，来严格控制大模型的COT过程，从而让大模型的思路严格按照人工客服的SOP流转的一种方式。

```python
{
  "状态路由":"初始化->需求总结->是否调用工具3->尺码表",
  "需求":"咨询尺码",
  "tool":"尺码表",
  "skill":"调用工具",
  "回复":""
}
```

只要在prompt里仿照人工客服的SOP定义清楚所有状态，并对不同的末尾节点定义不同的输出形式，即可实现类似Function Call的“选择调用工具或直接回复”功能。

通过状态机我们成功让大模型跟随了人工客服的SOP，并且可以自行选择调用工具或是直接回复。但是依然有多个问题需要解决：

●可迭代性差。基座模型在SOP转移细节上的理解与业务会有一定的gap，通常只能通过训练解决。但是在模型没有上线前，真实样本的收集较为困难。其本质原因是使用状态机表达的SOP与大模型原生的思考模式并不匹配，这种方式比较难发挥大模型的潜力。

●可维护性差。下图是状态机Prompt的拆解。对于商家的个性化要求或是SOP的更新，需要花大量精力修改适配Prompt，并且还需要通过离线测试集确保大模型对状态的理解与人工客服是一致的。

●优点：

○灵活性高，对于简单问题可以直接回复，复杂问题可以调用工具；

○以“工具调用”（数十种工具）取代了以往的“意图识别”（上千种场景），使得分类准确率更高。

●缺点：

○由于将状态机SOP嵌入，导致prompt极长，消耗资源过高；

○可维护性、可拓展性很差，既要调用工具又要回复的模式让所有模块耦合，不利于任务分解与迭代。

# 稳定性考量：拆分Planner和Responser

第一版Agent中将工具调用和回复全都由一个模型完成，虽然这非常符合agent的设计理念，但彼时基础模型（DeepSeek V3时期）的能力还没有达到一个非常强大的水平。当时，我们有以下几个观察：

❏不使用推理模型时，同时让一个模型执行两种任务（调用工具和回复），其准确率不会特别高，比不上写两套prompt后让模型分别执行两个任务；

❏使用推理模型时，不经训练的基础模型的RT（时延）对于店小蜜的线上业务是不可接受的。

基于业务的现实考量和以上两个制约条件，最终上线的版本选择了使用两个不同的模型进行工具调用和最终回复。

﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/f0458417-ab5f-4e4a-becd-40445356603c)﻿

拆分Planner和Responser﻿

●优点：

○目标导向：完成从SOP状态机到目标导向架构的转型，给予大模型更大的发挥空间，减少SOP不能考虑到的大量corner case，离线评测准确率达到91%；

○可维护性提升：解耦planner和responser后，两边模块可以分开迭代，提升合作效率。

●缺点：

○planner的思路直接给到critic时经常会与工具结果矛盾，导致回复不达预期；

○工程链路限制了工具只能调用一个，减少了复杂场景的可用性。

# 解锁更高上限：引入推理模型

解耦planner和responser的agent上线以后，相对于老的店小蜜机器人获得了超过约30%的转化率提升。但是由于使用了instruct版本（非推理版本）的planner和responser，其解决困难问题的能力依然不足。想要获得更强的解决问题的能力，我们需要在线上部署推理模型。而实现这一点在线上服务、推理资源、业务指标上有非常多的约束条件：

❏不经过训练的推理模型RT过长；

❏最大规模（如235B量级）的模型训练成本过高，以我们现有的资源基本只能支持到32B级别模型的后训练；最大规模的推理模型带来的线上RT也基本无法承受；

❏最大规模（如235B量级）的模型经实践，在业务指标上的表现要比小模型好得多。这是由于更大尺寸的模型能够记住更多的世界知识带来的优势。

| 业务指标（转化率、转人工率） | 更好✅ | 较低❌ |
| 困难case正确性 | 较低❌ | 更好✅ |

不同尺寸/推理模型的线上效果对比﻿

从上表可见，如果我们直接将responser从一个大的基座模型替换为小的推理模型，虽然能解决更多困难的case，给消费者带来更好的体验，但会损失业务指标。因此，有没有两全其美的方法呢？

推理Reflection帮助agent更好总结知识

## Planer的训练过程

店小蜜在FY26将原本的RAG框架升级成了Agent框架，整体框架发生了非常大的改变。特别的，在意图层面，由原先依赖“场景”、“正负例句”以及多个小模型的结构直接升级为了Planner架构。Planner负责在用户的每一个query进来后对用户的意图进行理解，给出回复思路，以及在必要时选择合适的工具。

﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/d3112f69-28dc-48fd-ae94-5a9747ee44cd)﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/18fe30f5-42c6-46d9-b9a3-c3a000c1113c)﻿

店小蜜Agent架构（左图）；店小蜜原RAG意图场景架构（右图）

在这个任务中，主要面临几个问题：

1.工具区分度不高：部分工具之间的定义可能较为模糊，对于模型理解区分度不高，直接将指令输入基座模型准确率不高，例如：

a.尺码表工具：当中包含的子工具——“常规选码”和“尺码属性”，分别是在用户想要询问应该穿什么尺码和询问某一尺码本身尺寸时调用，容易混淆。

b.活动工具：当中包含的子工具——“优惠活动”和“长尾活动”，分别解决范围都由各种活动概念组成，如前者解决“商品价格、满减满折、优惠券、品类券、百亿补贴”等问题，后者解决“好评返现、礼品卡、保价政策、淘金币”等问题，模型也难以直接理解

2.工具候选集变化频繁：随着业务的需要和agent中工具的迭代，会存在原有工具下线，或新工具上线的情况，对于分类问题来说泛化性要求较高

## 迭代过程

### 通用模型

2.1.1评测标准

在agent上线初期，由于缺少真实的线上多轮数据用于模型训练，于是需要选择最优的基座模型进行上线，所以优先需要一份评测集用于评测目前基座模型的能力强弱。针对planner选择工具后critic对于工具信息的处理方法，在标注时规定两个维度：

●最佳工具，best\_tool：单选；结合当前用户query和召回信息，最优先需要被选择到的工具，通常情况下为最符合使用场景的工具或所有工具都不符合时的无需工具（无需工具指不调用工具critic直接回复）。

●次优工具，correct\_tool：可多选；结合当前用户query和召回信息，不是最优先需要被选择，但选择也不会导致critic模型回复出错的工具，通常情况下为能够间接解决用户问题的工具或有工具符合使用场景但召回知识中也包含相关信息的无需工具。

将命中最佳工具和次优工具的比例分别作为严口径准确率和松口径准确率，评测通用基模如下

﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/40c086bc-160f-4ef6-905d-dd1f8d126291)﻿

根据以上评测结果以及rt要求，选择非推理模型deepseek v3做为初版模型上线。

#### Prompt设计

由于采用非推理模型，在prompt中让模型以依次输出\["用户需求","工具选择思路","选择工具"\]这几项元素，以COT的方式在非推理模型下提升模型选择工具准确率。

### DPO训练

在选用deepseek v3上线之后，线上遇到了以下几个问题：

●rt过长，资源消耗大：ds v3过大的模型尺寸导致线上推理时间较长，平均在4-5s；且部署需要的资源过大，成本较高

●badcase优化手段有限：只能通过修改prompt，增加few-shot例子来优化，优化范围有限，无法纠正模型自身的偏好

针对以上问题，需要采用训练的方式来优化模型本身，基于以往的经验，优先选择DPO作为训练方式。

2.2.1

#### 数据集构造

1.训练集

﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/f1eae1fe-c20e-437d-a7b0-94941474da9b)﻿

训练数据的构造pipeline大意可以由以上图示表示：

●训练数据集给到基座模型和人工标注分别得到工具选择，并比较两者是否符合。

●如果上述二者相符，则丢弃这条数据；若二者不相符，则保留基座模型生成的结果作为rejected answer，并进行chosen answer的继续生成。

●将同一份数据分别输入Deepseek R1, Deepseek V3, QwQ-32B（在2.1的评测中表现最好的三个模型）进行重生成，并与人工标注结果做比较。

●若上一步中比较一致，则取新生成的答案作为chosen answer，与rejected answer组成一对训练pair；若仍然比较不一致，则直接将人工标注结果一起输给Deepseek R1，进行正确工具答案的强行生成，作为chosen answer。

★需要注意：在第二步中为什么选择直接丢弃基座模型生成正确的数据，是考虑到模型在经过大量数据的DPO训练后，泛化性会损失较大，不利于后期新工具的上线和选择，所以在DPO训练时有意的只使用少量数据进行训练。

根据上述pipeline，最终实验中使用500条+条DPO训练数据。

### GRPO训练

DPO训练除了2.2中带来的好处以外，同样存在以下问题

●DPO训练中如果训练数据均为领域数据，随着数据量增多也会导致模型泛化性进一步的下降，不利于后续工具的灵活调整。

●随着开量商家的进一步扩充，模型对于数据数量和多样性的需求越来越大，这和上一条数据量多导致泛化性下降产生了一定的矛盾。

1.分类任务为什么选择GRPO作为优化算法：GRPO相比SFT和DPO等方法有保持高泛化性的优点，并且也能够大幅的提升准确率

### 4.Auto-Research（自动化探索评测prompt）

在优惠活动场景中，由于涉及高风险资损，人工标注时会考虑诸多细致的业务规则，这导致初版的自动化评测与人工标注一致性较差。为了提升评测结果的一致性，原始的基本方法是分析评测结果不一致的case、手动修改自动化评测prompt。这种手动分析和修改的方式存在效率低下的问题。  
受到context engineering自主进化框架思想的启发，我们提出了一套基于LLM的自动化评测prompt自主优化的方法。使用该框架在优惠活动场景的测试集上，自动化评测与人工标注的一致性从0.57提升至0.8。

#### 方案设计

我们采用如下pipeline进行评测prompt的自主优化，主要思想为在评测结果不一致的case上，基于LLM总结错误原因和prompt修改建议，进一步让LLM基于修改建议生成新的prompt，通过多轮迭代后不断优化prompt、提高评测一致性。

![image.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/8e89e1d5-ea94-4d3c-83f8-946171095c8f.png)

```python
Input:
    P₀          : 初始评测 prompt
    D_train     : 客服对话训练集 {(xᵢ, yᵢ)}，yᵢ 为人工评分
    D_eval      : 可选评估集
    T_max       : 最大迭代轮数
    acc_thres   : 准确率终止阈值

Output:    P*          : 优化后的最优 prompt
Begin:    P ← P₀    for t = 1 to T_max do:        // 1. 全局评测：用当前 prompt 推理所有样本        ŷᵢ = LLM(P + xᵢ) for all (xᵢ, yᵢ) ∈ D_train
    // 2. 计算准确率，收集错误样本
    acc = accuracy(ŷᵢ, yᵢ)
    E = {(xᵢ, yᵢ) | ŷᵢ ≠ yᵢ}
    
    // 3. 终止判断
    if E is empty or acc ≥ acc_thres:
        return P  // 收敛，输出最终 prompt
        
    // 4. 错误归因：输入编辑器，生成修改建议
    summary = "以下为自动评测失败案例：\n" + format_errors(E)
    suggestion_prompt = f"""
    原 prompt: {P}
    错误汇总: {summary}
    请总结共性问题，并提出一条简洁、通用的修改建议。
    输出格式：[最终输出] {"old_content": "...", "new_content": "..."}
    """
    raw_suggestion = LLM_editor(suggestion_prompt)
    
    // 5. 解析并更新 prompt
   
    ΔP = parse_json_patch(raw_suggestion)
    P ← apply_patch(P, ΔP)  // 替换 old → new

end for

return P  // 返回当前最优 prompt

End
```

### 5.针对业务指标的强化学习训练

大模型业务优化的一个重要难点是如何定义“好”的样本。在对话系统相关的业务中，随着基础模型的能力越来越强，离线评测和线上指标的背离成为常态：

●裁判模型认为这是个精准回复用户的问题的样本，但消费者看到准确却冗长的信息直接退出了对话界面；

●裁判模型给的标准答案是用户在当前场景下领不到券，但消费者的潜在意图却是让智能客服告诉他什么时候能领到券，他应该去做什么；

我们的第一个想法是使用线上指标直接作为单样本偏好数据训练模型。涉及线上指标的数据集有其特殊性：以转化率指标为例，每一个样本只有一个结果，代表转化/不转化，不存在同一个问题下的两种回复，因此不能使用DPO这种需要1Q（question） 2A（answer）的训练算法。对于这种情况，我们引入KTO\[1\]算法训练：

﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/5e052b4d-ba63-47db-9ea7-17405b68384a)﻿

KTO算法允许1Q 1A的数据集构造。只需要将线上收集的样本按照指标区分为正负样本（如：用户下单的为正样本，用户未下单的为负样本），即可获得单样本的偏好数据集。该方法的结果如下：

|  | 离线评测准确率（相对值） | 在线指标（相对值） |
| --- | --- | --- |
| KTO模型 | +2% | +约1% |

直接基于线上指标训练模型后，我们遇到了两个比较大的问题：

●以线上指标为标签训练的模型为了指标无所不用其极，会存在极端badcase不符合道德准则或服务规范模型在无确定知识的情况有时会信口开河

●线上业务的分布偏移无处不在：每一次商家扩量、每次一次季节变更都有可能让模型的效果下降。用夏天的转人工率训练的服饰客服在秋天到来时，效果很容易比不上基础模型。

## 富文本信息的引入

店小蜜业务与ChatGPT、元宝等纯对话场景相比，有一个重要差异是客服机器人是一个富文本场景。用户与客服的对话中包含了大量的卡片、图片、链接等富文本信息；

﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/b4c0ee95-a7e9-4a2e-9d29-d06ee1cad567)店小蜜对话场景﻿

如何让LLM“看懂”这些商品选择卡片，使得LLM看到的场景与用户看到的场景一致呢？一个直观的方式是直接将所有卡片内的有效信息用结构化文本的形式表达：

用户看到的卡片

﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/a9b82dfc-5827-409d-b1e0-c2ca99ab5a65)﻿

大模型看到的文本

```python
大模型看到的文本
{
"role":"user",
"content":"<卡片消息>用户发送了一条商品链接
商品名称是：KWV真维斯白色短袖t恤女2025新款夏季长袖内搭小上衣纯棉打底衫女
商品id是：808924910043</卡片消息>"
}
```

通过将所有富文本信息使用类似于“<卡片消息></卡片消息>”的方式文本化表达以后，我们基本做到了大模型看到的上文与用户看到的信息一致。然而，在测试过程中遇到了这样一个case：

```python
[
  {
    "role": "system",
    "content": "你是一个淘宝客服专家..."
  },
  {
    "role": "user",
    "content": "<卡片消息>用户发送了一条商品链接\n白色连衣裙</卡片消息>有没有黑色的"
  },
  {
    "role": "assistant",
    "content": "亲亲看看这个哦<卡片消息>客服发送了一张推荐卡片\n黑色连衣裙</卡片消息>"
  },
  {
    "role": "user",
    "content": "还是白色的吧，链接发我"
  }
]
```

在上文的第一轮回复中，实际上调用了“商品推荐”工具。在大模型回复“亲亲看看这个”之后，工具紧接着给用户吐出了一张推荐卡片。然而，将这些文本化的对话输入大模型后，模型的输出为：

```python

[
  {
    "role": "assistant",
    "content": "好的，亲亲，这是链接哦～<卡片消息>用户发送了一条商品链接\n白色连衣裙</卡片消息>"
  }
]
```

我们会发现大模型模仿上文格式化的富文本信息，自己产出了一个<卡片消息>。然而这个<卡片消息>一般是无法被工程代码解析的，所以很难将这种文本化的语言重新翻译为卡片给用户发送。因此，我们需要严防大模型模仿上文输出类似的格式化信息。

在多次尝试调整Prompt失败后，我们找到的方法是将所有role为“assistant”的<卡片消息>的“role”修改为“tool”——再次使用一半的function call协议，就能让大模型意识到上文这些格式化的文本不是自己回复的，从而避免这种问题。

在这个场景下，非标准的function call协议在满足OpenAI格式的前提下为我们在对话中引入了第三方（也就是Tool）的发言，从而消弭了纯对话场景与店小蜜业务场景的差距。

## Executor一定要是LLM吗？

不一定。在店小蜜售前对话中，有一些高危场景是不适合用LLM对话的，比如用户询问优惠券的场景。一方面（非推理）大模型对数字相关问题处理能力不足，另一方面涉及“💰”的情况下一般商家会希望能出相对固定的话术，而不是完全交给prompt工程和大模型自由发挥。

所以我们需要再给agent套上一把锁，整体链路如下：

﻿![image](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/oJGq75kxg7ZeBlAK/img/1b234231-8e23-48ad-b4f7-e1d0db256b17)﻿﻿

通过每个工具自主判断是否需要LLM Executor，如果不需要则通过规则直接输出结果，否则则将工具结果返回给大模型并生成最终回复。这种“双轨制”的executor能够在灵活结合业务规则的情况下最大程度发挥大模型的对话能力。
